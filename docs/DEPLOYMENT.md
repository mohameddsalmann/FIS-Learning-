# Deployment runbook

## Local and CI

Use Node 22.13+ in the 22.x line or Node 24.x and install with `npm ci`. For private local journeys, create an isolated PostgreSQL database with pgvector, set a local `DATABASE_URL`, set a distinct `BETTER_AUTH_SECRET` of at least 32 characters and configure the exact local origin in `BETTER_AUTH_URL` and `APP_URL`. Execute `npm run db:deploy` and `npm run dev -- --port 3100`. Connect a private Blob store and at least one eligible provider for the live study flow. `.env.example` lists supported settings. The optional example lessons are pre-authored and require no provider credentials.

GitHub Actions verifies migrations against disposable pgvector/PostgreSQL, checks types and lint, runs unit/integration tests and the prepared evaluation, builds the app with generated Prisma Client, and runs Chromium browser tests. `FIS_INTEGRATION_DATABASE=isolated` enables the isolated mutation tests only on loopback. `FIS_TEST_DB=1` enables the authenticated browser test.

## Isolated hosted preview

1. Create or select the intended Vercel project and connect this GitHub repository. `vercel.json` selects Next.js with `npm ci` and `npm run build`. Confirm the framework and build settings in the target project before deployment. `.vercelignore` excludes actual environment files, local legacy jobs and the legacy Express shell. [Vercel framework configuration](https://vercel.com/docs/project-configuration/vercel-json), [deployment file exclusions](https://vercel.com/docs/deployments/vercel-ignore).
2. Connect an isolated Neon branch or database with pgvector. Add `DATABASE_URL` to Vercel Preview using the pooled runtime connection. Use the same database for the protected GitHub Preview migration secret. If a separate direct migration connection is needed, set `DIRECT_URL` in the GitHub environment. If installing Neon through Marketplace, have the account owner review and accept its terms and select the Free plan (`free_v3`). Review the migration on the preview database. [Vercel Neon Marketplace](https://vercel.com/marketplace/neon), [Neon preview branches](https://neon.com/blog/neon-vercel-native-integration).
3. Connect a **private**, Preview-only Blob store and add `BLOB_READ_WRITE_TOKEN` plus an independent Better Auth secret to Vercel Preview. Let Better Auth use the generated deployment origin when `VERCEL_URL` is exposed, or set the exact preview origin in `BETTER_AUTH_URL` for an intended stable preview domain. Use that same origin in `APP_URL` for server-side origin checks when configuring a stable domain. Open the intended origin consistently during tests. [Vercel private storage](https://vercel.com/docs/vercel-blob/private-storage), [Vercel system variables](https://vercel.com/docs/environment-variables/system-environment-variables).
4. Configure `OPENROUTER_API_KEY` for verified free chat and embedding routes, or record confirmed Google project free-tier eligibility before enabling Gemini in that environment. Use `GEMINI_API_KEY_PRIMARY` or its `GOOGLE_API_KEY` alias, paired with `GEMINI_PRIMARY_FREE_TIER_CONFIRMED=true`. Set `GROQ_API_KEY` and `GROQ_FREE_PLAN_CONFIRMED=true` only for a confirmed GroqCloud Free account. Groq adds tutor routes and the document pipeline still requires an embedding provider. `XAI_API_KEY` is optional and xAI inference remains disabled without explicit eligible authorization. See [AI models](AI_MODELS.md) for the routing details.
5. Configure the protected GitHub `preview` environment with `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID`, `VERCEL_TOKEN`, `DATABASE_URL`, and optional `DIRECT_URL`. Keep automatic production promotion disabled before making the workflow available on the default branch. Dispatch `Deploy verified FIS release` against the reviewed branch with `preview`. The workflow runs CI, checks the selected files and hosted environment variable names, applies Prisma migrations against the selected database, runs a remote Vercel build, and checks the generated HTTPS deployment. Runtime credentials stay in Vercel. [Vercel CLI deployment](https://vercel.com/docs/cli/deploy), [Vercel CLI health requests](https://vercel.com/docs/cli/curl).
6. On that HTTPS preview, sign in as two separate test users. Upload a synthetic PDF, verify that indexing advances automatically, and check that the second user cannot open the file. Ask a course question, open and close the citation beside the answer, and request a visual explanation. Test the direct upload path on a safe synthetic file above the 4 MiB server-upload threshold. Run a Quick Quiz, submit it, and reload Progress. Also check Arabic on mobile, guided Help, provider failures, sign-in and guest account conversion. Record each status without credential values or student data.

## Production release

1. Review the successful preview and agree the production target. Configure the protected GitHub `production` environment with production-specific migration credentials and Vercel access, and require reviewers. Use a separate Neon database or branch, private Blob store and Better Auth secret, and set `BETTER_AUTH_URL` and `APP_URL` to the canonical production origin. Verify provider credentials separately. Keep Vercel Git auto-promotion disabled when using this release path.
2. Apply reviewed migrations through the workflow on the default branch. The `production` target stages a production build with `--skip-domain`. The workflow checks the generated HTTPS URL, free chat and embedding catalog status, and unauthenticated access boundary. The preview is where the complete authenticated journey is verified, because production auth is scoped to its canonical origin. [Vercel staged promotion](https://vercel.com/docs/deployments/promoting-a-deployment).
3. After authorization and verification, promote the staged deployment with `vercel promote <deployment-id-or-url>`. Smoke-test the canonical HTTPS domain. If the release fails, use Vercel rollback after confirming schema compatibility. Repair schema issues with a forward migration.

## Deployment verification

No hosted Vercel deployment or environment configuration is verified by this repository snapshot. Before deploying, follow the preview steps above and confirm the target project's database, private Blob store, authentication secret, and eligible AI provider settings. Keep production deployment behind the protected release workflow.
